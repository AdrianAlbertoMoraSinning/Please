ARCHITECTURE IMPLEMENTED
PLEASE business transaction
  -> PostgreSQL source-table trigger / durable event
  -> please_accounting_outbox
  -> scheduled Accounting Worker
  -> posting rules
  -> atomic PostgreSQL Journal posting RPC
  -> Journal / Ledger / Tax / Financial reporting foundation

ACCOUNTING SAFETY
- Operational actions no longer wait for synchronous CAL posting.
- Financial events are created durably by PostgreSQL triggers from the same source-table transaction.
- Queue states used by STEP 17: PENDING / PROCESSING / POSTED / RETRY / IGNORED / DEAD_LETTER.
- Legacy ERROR is accepted only as rollout compatibility with STEP 16 and is recoverable by the new worker.
- Worker claims use FOR UPDATE SKIP LOCKED.
- Event keys, source references, event versions and payload hashes enforce idempotency and traceability.
- Journal header + lines + POSTED state + event linkage are completed by one PostgreSQL RPC transaction.
- Posted Journal headers and posted Journal lines are immutable.
- Corrections use reversal entries rather than silently changing posted accounting.
- Issued invoice financial values are locked in Admin; correct by void/reissue.
- Stripe customer payments use Stripe Clearing; Stripe fees are separate events.
- Provider costs recognize a payable before the provider payment clears it.
- Dependency waiting does not consume retry attempts.
- Repeated real failures move to DEAD_LETTER instead of retrying forever.
- Dead-letter requeue resets retry budget for a controlled recovery attempt.
- Refunds are recorded for accounting review but are NOT auto-posted until PLEASE has a dedicated Refund/Credit Note source-document workflow.

ROLLBACK / PAUSE PRINCIPLE
If the worker must be paused after deployment, disable the STEP 17 worker/integration in the runtime configuration rather than deleting queue rows or accounting history. Durable events should remain in the database for later processing/recovery. Never delete an event merely because processing failed.
